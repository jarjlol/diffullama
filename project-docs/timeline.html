1. The project in short

The course project is an "AI-augmented research cycle". It has six stages. Each stage pairs a usual research step with an LLM-assisted method. The stages are: idea extraction, reproduction, idea enhancement, implementation, paper writing, and review.

Source: project-docs/01-project-brief.md, "The project format".

The anchor paper is Scaling Diffusion Language Models via Adaptation from Autoregressive Models (Gong et al., ICLR 2025, arXiv:2410.17891). The paper changes a pretrained autoregressive (AR) model into a masked diffusion language model (DLM). It makes DiffuGPT (124M and 355M) and DiffuLLaMA (6.74B). The team uses a fork of the authors' code.

Source: 01-project-brief.md, "Anchor paper"; decision D-2026-08-13-a.

5. Task 4 (codification) in detail

5.1 What the brief asks

The brief has five parts. Each part has a place in codification/ITERATION_1.md:

  1. Codify the best idea with LLMs. The team uses Arbor. An LLM changes the selection code, and Arbor keeps a change only if it is better on held-out data.
  2. Find spec gaps and infeasibilities. The issue log has I-1 to I-20.
  3. Refine the idea with feedback to the model. Each reply to Arbor is in §Arbor.
  4. Get final results on a metric and a dataset: GSM8K accuracy, in §Results.
  5. Compare with SOTA and baselines. Majority vote (self-consistency) is the main baseline. Published numbers are a check on the generation.

Source: codification/ITERATION_1.md, "What the brief asks for".

5.2 The idea (1.1)

A diffusion model writes N = 10 answers to each GSM8K maths question. A small AR model gives each answer a score (its negative log-likelihood, NLL). The method selects the answer with the best score. The idea says: the accuracy that this recovers depends on how much of its AR base the diffusion model keeps. CKA between the two models, layer by layer, measures this.

Source: codification/IDEA_SELECTION.md; codification/README.md.

5.3 The pipeline

1 DataGSM8K: dev 200 (from train), test 500 (from the official 1319)
2 Generate10 answers per question, for each of 5 DLMs
3 ScoreNLL of each answer under 5 AR scorers
4 CKAEach DLM against its AR base, 4 models
5 ArborAn LLM changes solution.py; merge only on gain
6 Evaluate300 final questions; paired statistics

Source: codification/pipeline/ (one script for each step); codification/ITERATION_1.md, "Run plan"; codification/split_gate_final.py.

5.4 The Arbor loop and the feedback

Arbor ran in review mode. In this mode a person checks each idea before Arbor runs it. The LLM was Qwen3.8-27B-FP8 on a local vLLM server. The main feedback was:

  • Arbor proposed twice to use other models' answers to the same question. The reply rejected this both times. That is ensembling across models, and it is not fair to the per-model baselines.
  • A reply corrected a wrong fact: LLaDA has no AR base.
  • A reply gave a new direction: check the arithmetic in each answer, and use the result as a vote weight. This became idea 4.1, the one that Arbor merged.
  • A reply told Arbor not to tune the weight on dev data, because a tuned weight would overfit.

Source: ITERATION_1.md §Arbor (replies verbatim); codification/results/iter1/arbor_session/; codification/results/iter1/ops/start_vllm.sh.

Finding 1. Idea 1.1 as written is refuted. On Dream, the best AR pick (32.0) is worse than the first sample (41.0). On LLaDA it is almost the same (52.0 against 48.7). Majority vote is more than 20 points better than each AR pick on both models. The result stays the same when each model's own 7B base is the scorer.

Finding 2. The best selector is equal to majority vote. Arbor's merged rule 4.1 has no significant difference from majority vote on any split. Arbor's merge gate compared 4.1 with the seed rule (GPT-2 NLL, 0.157), not with majority vote. So the merge does not show that 4.1 is better than majority vote.

Finding 3. Majority vote gives a large gain. Against the first sample, 4.1 adds +32.0 points on Dream (p = 8e-27) and +24.3 on LLaDA (p = 2.5e-16). Majority vote closes 61% to 69% of the distance from the first sample to the oracle.

CKA against headroom

The idea predicts: a higher CKA gives more gain from AR reranking. Spearman ρ is positive for all 10 AR selectors (+0.4 to +1.0). But only 4 models have an AR base. With 4 models, the smallest possible p is 0.083. Three of the four models are near 0% accuracy. So the order comes from Dream only. LLaDA has no AR base, and it also loses with most AR scorers. This result is descriptive only. It is not evidence.

Source: ITERATION_1.md §Results, "CKA vs headroom"; codification/results/iter1/numbers/analyze_test500.txt.

Lessons from operations

  • A vLLM server held a shared GPU for about 8 hours with no work, while a decision was not made. Rule now: start the server together with its job, and stop it when the job ends.
  • vLLM for Arbor needs a 131072-token context. The first Arbor run failed at 32k on its 4th turn.
  • Tensor-parallel vLLM hangs on Blackwell. Data-parallel works.
  • Answer Arbor's review prompts with its commands (/approve, /edit, /answer). Plain text goes to a helper LLM, which is slow.

Second review of what to borrow (6 November 2026)

We read the four papers a second time, independently, at their arXiv full text. We also read Arbor's own code (version 0.1.4). The review agrees with the table above and adds twelve mechanisms (B-12 to B-23). It also found problems in how we set up Arbor.

Safety problems.

  • Arbor's memory of iteration 1 (EXPERIENCE.md) lists cross-model consensus as a useful finding. We rejected that idea twice. If iteration 2 reuses the file unedited, Arbor gets the banned idea back. T3 now writes a corrected copy.
  • eval.py lets the selection rule keep information from one question to the next. That is how Arbor built the cross-model cache. T1 now drafts a check that runs the rule in two orders and fails it if any choice changes.

Arbor settings we misread.

  • merge_threshold does not block merges. Arbor merges on any held-out gain, however small. The reviewer must enforce a margin (at least 3 questions net).
  • Arbor reuses earlier runs' memory only in its chat start-up, not with arbor run, which is how we start it.
  • Arbor's own guards were all off in iteration 1: protected files, plugins, and the plateau detector. T1 now writes a plugin that turns them on.

12. Terms

TermMeaning
AR modelAutoregressive language model. It writes one token at a time, from left to right.
DLMDiffusion language model. It starts from masked tokens and fills them in over many steps.
CKACentered kernel alignment. A number from 0 to 1 that shows how similar two models' hidden layers are.
NLLNegative log-likelihood. A lower value means the scorer model finds the text more likely.
First sampleUse the first of the 10 answers. This is the simplest baseline.
Majority voteUse the answer that most of the 10 samples give. Also called self-consistency.
OracleThe question counts as correct if any of the 10 answers is correct. No real method can do better.
Headroom(selector − first) / (oracle − first). The share of the possible gain that a selector gets.
McNemar testA paired test. It uses only the questions where the two methods give different results.
ArborAn LLM research system (arXiv:2606.11926). It suggests changes, tests them on dev data, and merges a change only if a held-out test improves.
Dev / gate / finalDev: 200 questions for Arbor to try ideas. Gate: 200 test questions for Arbor's merge check. Final: 300 test questions that Arbor never sees.
