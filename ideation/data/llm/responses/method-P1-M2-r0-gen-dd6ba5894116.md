**Method**

| Step | Action & Details | Resources & Timeline |
|------|------------------|----------------------|
| **0. Project scaffolding** | Create a shared Git‑LFS repo with a `conda‑environment.yml` (CUDA 12.4, PyTorch 2.4), a minimal `dockerfile`, and a lightweight job‑scheduler (e.g., GNU parallel or `ray`) to distribute GPU jobs among the three GPU‑enabled teammates. CPU‑only teammates handle tokenisation, prompt‑stratification, and metric aggregation. | ½ day |
| **1. Model & backbone selection** | Choose **four** released DLMs to increase statistical power while staying inside the 96 GB memory envelope: <br>• DiffuGPT‑S (127 M, GPT‑2‑based) <br>• DiffuGPT‑M (355 M, GPT‑2‑based) <br>• DiffuLLaMA (6.74 B, LLaMA‑2‑based) <br>• Dream‑7B (7 B, LLaMA‑2‑based) <br>For each DLM retrieve its AR base (GPT‑2‑small for the GPT‑2 family; LLaMA‑2‑7B for the LLaMA family). No fine‑tuning or continual‑pre‑training is performed – the study is strictly inference‑only. | 0.5 day |
| **2. Prompt pool construction** | Build a stratified prompt set of **300** instances (100 each from HumanEval, GSM8K, SIQA/WinoGrande). Within each dataset split the prompts into three difficulty tiers (easy, medium, hard) based on the baseline performance of the AR backbone (pass@1 for HumanEval, exact‑match for GSM8K, accuracy for SIQA/WinoGrande). For each tier create balanced mini‑batches of size = 4 (mixed domains) to maximise GPU utilisation. | CPU‑side: 1 day |
| **3. Representation‑preservation profiling across denoising timesteps** | For every DLM‑backbone pair: <br>a. **Forward pass of the AR backbone** on the *ground‑truth* target sequence (prompt + reference completion) to obtain frozen hidden‑states **h⁽ᴬᴿ⁾ₗ** for each transformer layer *l* (fp16, no gradients). <br>b. **Diffusion sampling** with the model’s native scheduler. At each denoising timestep *t* (t = 1…T, where T is the maximum step budget we will test, i.e., 256) we capture the model’s *denoised‑token prediction* **x̂₀⁽ᵗ⁾** (the model’s estimate of the clean sequence after step *t*). <br>c. Run a **forward pass of the DLM** on **x̂₀⁽ᵗ⁾** (teacher‑forcing style) to obtain hidden‑states **h⁽ᴰᴸᴹ⁾ₗ,ₜ** for each layer *l*. <br>d. Compute **Centered Kernel Alignment (CKA)** between **h⁽ᴰᴸᴹ⁾ₗ,ₜ** and the frozen **h⁽ᴬᴿ⁾ₗ** for every layer *l*, then average across layers to get a scalar **Cₜ** (alignment at timestep *t*). <br>e. Store the full alignment curve **{C₁, C₂, …, C_T}** for each prompt. <br>Because the curves are needed only for a representative subset, we compute them on **50 randomly selected prompts** (≈ 1⁄6 of the pool). The remaining 250 prompts are used only for the downstream QET measurements (see Step 4). <br>Implementation notes: <br>– Use activation‑checkpointing so that the intermediate hidden‑states for each timestep do not exceed GPU memory. <br>– For DiffuLLaMA (6.74 B) also keep a full‑precision copy for the alignment computation; the 4‑bit quantisation used later for generation does **not** affect the CKA because it is applied *after* the hidden‑states are extracted. | Approx. 8 GPU‑hrs (CKA per timestep is cheap; the dominant cost is the diffusion forward passes, which are already required for generation). |
| **4. Deriving a scalar “alignment‑efficiency” metric** | From each alignment curve **Cₜ** compute: <br>• **Asymptotic alignment**  C∞ = maxₜ Cₜ (the highest alignment reached within the tested step range). <br>• **Alignment‑efficiency (AE)** = the smallest timestep *t* such that Cₜ ≥ 0.9 · C∞ (i.e., the step at which 90 % of the attainable alignment is achieved). If the curve never reaches 90 % we set AE = T (the maximum step budget). <br>AE captures how quickly the DLM’s internal representations become AR‑like during denoising: a low AE means the model aligns early (high representation preservation), a high AE means alignment is delayed (low preservation). <br>Average AE across the 50 profiling prompts to obtain a single **AE score per DLM**. | CPU‑side: negligible (< 0.5 hr). |
| **5. Candidate generation for QET measurement** | For **each** DLM (all four) and **each** prompt in the full 300‑prompt pool: <br>– Run the native diffusion sampler at three step budgets: **Low = 16**, **Medium = 64**, **High = 256** steps. <br>– At each budget generate **N ∈ {1, 2, 4, 8}** independent samples (different seeds). <br>– Use fp16 + activation‑checkpointing; for DiffuLLaMA additionally test 4‑bit quantisation *only* for the generation phase (the alignment computation in Step 3 stays in full precision). <br>– Store the generated token sequences (as IDs) to avoid recomputation for scoring. | Rough estimate: 300 prompts × 4 (N) × 3 (step budgets) × 4 (models) = 14 400 generations. With batch‑size = 4 and activation‑checkpointing → ≈ 22 GPU‑hrs (well under the 30 GPU‑hr budget). |
| **6. Lightweight AR reranking** | Load a tiny AR scorer (GPT‑2‑small, 124 M) in fp16. For each set of N candidates compute the **average negative log‑likelihood (NLL)** of the full sequence (including EOS). The candidate with the lowest NLL is selected as the “sampling + reranking” output. The scorer runs on a single CPU core; its latency is overlapped with GPU kernel launches via CUDA streams, so its overhead is negligible for the efficiency metric. | CPU‑only; < 0.5 GPU‑hr equivalent. |
| **7. Quality evaluation** | For every output (denoising‑only and sampling + reranking) compute three task‑specific scores: <br>• HumanEval pass@1 and pass@10 → averaged → **code score**. <br>• GSM8K exact‑match accuracy. <br>• SIQA/WinoGrande accuracy (averaged). <br>Normalise each raw score to \[0,1\] across **all** conditions (model × step × N × strategy). <br>Take the unweighted mean of the three normalised scores → **Quality** ∈ \[0,1\]. | CPU‑side: < 1 hr. |
| **8. Efficiency measurement & QET** | Measure **wall‑clock latency per generated token** (including scorer overhead for the reranking condition) using `torch.cuda.Event` timestamps, averaged over all prompts and repetitions. <br>Convert latency to **Estimated Compute**:  `EstCompute = latency_per_token × peak_FP16_throughput (≈ 140 TFLOPs)`. <br>Define **Quality‑Efficiency Trade‑off (QET) = Quality / EstCompute**. Higher QET → more quality per unit of compute. | GPU‑side timing; negligible overhead. |
| **9. Analysis pipeline** | 1. **Marginal QET gains**: <br> a. ΔQET_denoise = QET(high steps, N=1) − QET(low steps, N=1) (and low→medium, medium→high). <br> b. ΔQET_sample = QET(medium steps, N=8) − QET(medium steps, N=1) (and 1→4, 4→8). <br>2. **Preservation‑Gain Relationship**: Compute **Spearman’s ρ** between each model’s **AE** (from Step 4) and the two sets of marginal gains (ΔQET_denoise, ΔQET_sample). <br>3. **Interaction test**: Fit a **linear mixed‑effects model** <br> `QET ~ AE * step_budget * N + (1|model) + (1|prompt_difficulty)` <br> including **model_family** (GPT‑2 vs. LLaMA) as a fixed effect to test whether the slope of AE differs across families and step budgets. <br>4. **Bootstrap uncertainty**: Resample prompts (with replacement) 1 000 times, recompute AE, QET, marginal gains, and correlations; report 95 % confidence intervals. <br>5. **Decision‑rule exploration**: Derive a simple threshold policy: if AE < τ (i.e., the model aligns quickly) allocate extra compute to **sampling + reranking**; otherwise allocate to **more denoising steps**. Optimise τ on a held‑out 20 % of the prompt set via grid search and report the resulting QET improvement over a uniform‑step baseline. | Analysis (CPU): ≈ 2 days. <br>Bootstrap (1 000 × lightweight recompute): ≈ 6 GPU‑hrs (can run overnight on a single GPU). |

Validation & robustness** | • **Ablation of alignment metric**: repeat Steps 3‑4 using **SVCCA** and **linear‑probe AUC** (instead of CKA) to ensure conclusions are not metric‑specific. <br>• **Quantisation sanity check**: compare QET curves for full‑precision vs. 4‑bit DiffuLLaMA to confirm that quantisation does not flip the observed trend. <br>• **Alternative scorer**: repeat reranking with a 30 M‑parameter distilled GPT‑2 to verify that scorer size does not drive the AE‑QET relationship. | Additional ≈ 4 GPU‑hrs. |

**Rationale**

The existing proposal treats *representation preservation* as a static, layer‑wise similarity (CKA) measured once between the final DLM and its AR backbone. While useful, this approach discards the **dynamic information** that is intrinsic to diffusion models: the degree to which the model’s internal representations become AR‑like *as denoising proceeds*.  

Our method introduces an **alignment‑efficiency (AE)** metric that captures *how quickly* a DLM’s hidden states converge to those of its autoregressive predecessor during the denoising trajectory.  

- **If a DLM preserves AR representations well**, we expect its internal states to align early (low AE). In this regime, additional denoising steps yield diminishing returns because the model is already close to the AR prior; spending compute on generating more candidates and reranking them with a tiny AR scorer should therefore give a larger QET gain.  
- **If preservation is poor**, alignment is delayed (high AE). The model needs many denoising steps to bring its representations into alignment with the AR prior, so investing compute in extra steps is likely to improve QET more than simply sampling more candidates.  

By correlating AE with the *marginal* QET gains from each compute‑allocation strategy (more denoising vs. more sampling + reranking), we directly test the hypothesis that the *shape* of the representation‑alignment curve—not just its final similarity—determines the most effective way to spend inference budget.  

The mixed‑effects model and interaction terms let us examine whether this relationship differs between GPT‑2‑based and LLaMA‑based families and whether it varies with the denoising‑step budget, addressing the second part of the research problem.  

Finally, the derived threshold policy (AE < τ → sample + rerank; else → more steps) translates the scientific finding into a practical, inference‑time rule of thumb for practitioners deploying scaled diffusion language models, fulfilling the goal of providing a principled diagnostic tool rather than a new training method.  

Overall, the method stays strictly inference‑only, respects the RTX 6000 Pro Blackwell memory limit, fits comfortably within a ten‑week timeline, and leverages only publicly released checkpoints and standard evaluation harnesses.
